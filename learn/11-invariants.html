11.3 Rejection must preserve state

A diver cannot spend air that is not in the tank. Returning false after subtracting too much would be too late: the tank would already contain an impossible value. A reliable object checks a proposed change before committing it.

A promise that survives every operation

void main() {
    Tank tank = new Tank();
    IO.println("Use 3: " + tank.use(3));
    IO.println("Air: " + tank.air());
    IO.println("Use 4: " + tank.use(4));
    IO.println("Air: " + tank.air());
}

class Tank {
    private int air = 5;

    int air() {
        return air;
    }

    boolean use(int amount) {
        if (amount <= 0 || amount > air) {
            return false;
        }
        air = air - amount;
        return true;
    }
}

Open learn/examples/11/AirTank.java. An invariant is a condition that must remain true whenever an operation finishes. This tank starts with air 5 and promises never to go below 0. Every accepted use must be positive and no greater than the available air.

Private marks air as an internal implementation detail rather than a public field for unrelated code. Our caller reads it through air() and requests changes through use. Keep that boundary: changing fields directly would bypass the rules those methods implement.

Use first checks the whole request. An invalid amount returns false before the assignment. A valid amount is subtracted once and returns true. Trace the calls: 3 leaves 2; the rejected 4 leaves exactly the same 2, not 0 and not -2.

Predict a boundary request

Using exactly 2 at that point succeeds and leaves 0. What about using 0? It is rejected here because the rule explicitly requires a positive amount. Different rules are possible, but caller and implementation must agree.

Task: protect both ends of the fuel gauge

Open learn/practice/11/FuelTank.java. Fuel starts at 5 and must remain between 0 and capacity 10. Refill accepts only a positive amount that fits. Travel accepts only a positive cost that is available. Reject other requests with false and no fuel change.

Refill 3 then travel 4 must give true, fuel 8, true, fuel 4. Refill 6 then travel 0 must reject both and keep 5. Refill 5 then travel 10 reaches 0 legally. Negative requests must also fail without mutation.

Hint 1: validate before writing

Guard each assignment. A rejected operation must preserve the old value rather than clamp it to a boundary afterwards.

Hint 2: measure free space safely

Compare the refill amount with 10 - fuel. This also rejects a huge positive int without overflowing while trying to add it first.
