14.1 Choose examples that catch mistakes

A result that looks plausible is weak evidence. A functional check calls a rule with known input and compares its returned value with an independently chosen expectation. It should explain the difference when the two disagree.

14-checks-and-exploration/P01_Example_StreakChecks.java

/// # Worked example · 14.1 Choose examples that catch mistakes
/// Lesson: 01-checks.html

int boost(int streak) {
    return streak >= 3 ? streak * 2 : streak;
}

void equal(int expected, int actual, String name) {
    if (expected != actual) {
        throw new AssertionError(name + ": expected " + expected + ", actual " + actual);
    }
}

void main() {
    equal(0, boost(0), "empty streak");
    equal(2, boost(2), "before the boundary");
    equal(6, boost(3), "first doubled streak");
    IO.println("PASS 3 checks");
}

The equal helper throws AssertionError on disagreement. Its name is ordinary code, not special test syntax. Expected goes first, actual second. A thrown error prevents the final PASS message, so success means all preceding checks completed.

Expected values come from the stated rule, not by copying the implementation’s expression into the check. Otherwise the same mistake could be repeated on both sides. Use a typical value, boundaries and any special case.

Would a weaker check notice?

If boost incorrectly used > 3, the checks for zero and two would pass. The input three returns three instead of six and exposes the mistake. What extra input would examine the rule after the boundary?

Task: test the delivery rule

In 14-checks-and-exploration/P02_Task_DeliveryChecks.java, author examples, not a new price formula. Distances zero through three cost two; distances four through nine cost five. Each Example stores an input and your expected result. Use only inputs 0..9.

Include the last nearby distance and a far distance. Check the stated endpoints too. The supplied verifier first accepts the correct price rule, then asks whether your examples reject three deliberately wrong rules: a shifted boundary, always two, and always five.

IntUnaryOperator is a supplied role taking one int and returning one int. applyAsInt invokes that role. The method reference this::price passes this program’s price behaviour without calling it yet; the later lambdas provide the wrong alternatives.

Hint 1: make the wrong boundary disagree

Choose an input where distance < 3 and distance <= 3 give different answers.

Hint 2: include both prices

A suite containing only nearby inputs cannot reject the always-two rule. Add a correctly priced far example.

These checks examine behaviour, not formatting or method names inside the implementation. Next you will define your own role so different objects can supply interchangeable behaviour.

Practise in a game

  • Hanoi · 14-checks-and-exploration/P03_Task_Hanoi.java
    In Hanoi find the shortest two-attempt witness of placing a larger disc illegally. The first move succeeds; the second leaves the tower unchanged.
  • LightsOut · 14-checks-and-exploration/P04_Task_LightsOut.java
    Design at most two two-click LightsOut tests that distinguish all six counterfeit rules. Overlapping toggles cancel; derive expectations on paper first.
  • Tents · 14-checks-and-exploration/P05_Task_Tents.java
    Expand Tents' learnerChecks with occupied and empty positions and swapped axes. One tree does not prove correct reading of the whole map.
  • PegSolitaire · 14-checks-and-exploration/P06_Task_PegSolitaire.java
    Write legal and illegal jump examples for PegSolitaire on the same initial board. Data coordinates start at zero; player-facing coordinates at one.
  • Merge2048 · 14-checks-and-exploration/P07_Task_Merge2048.java
    Add Merge2048 examples of rows after moving left and the points earned. A newly merged tile cannot merge again in that move.

The source also contains the task and controls. Check your selected game using Check.java in the same folder; the setup lesson explains how.
